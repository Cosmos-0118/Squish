# PDF and Office optimiser v2: real-world verification

Branch `perf/pdf-office-optimiser-v2`, nothing committed. Everything below was run against the final code (313 unit tests pass), on Windows 11 with the repo's bundled qpdf 12.4.2 / oxipng / pngquant / mozjpeg.

## What was tested, and with what

| Area | Inputs | How it was checked |

## Verdict

- **No compatibility failure was found** in anything the optimiser produced and left in place: 0 qpdf errors, 0 package problems, 0 repair dialogs or open failures in Word/PowerPoint/Excel, and LibreOffice converted every file without error, page counts and extracted text identical on every file, ODF `mimetype` first and stored, EPUB valid under epubcheck (and an invalid source, `mimetype` last, came out valid).
- **Verification found four defects in my own implementation; all four are fixed in the working tree** (details below). Unit tests for each were added. The numbers in the tables are from after the fixes.
- Risks that remain are listed under "Known limits". The important ones: aggressive mode removes borders/fills of blank formatted areas (documented behaviour, but it hits printable templates), peak memory is around 1 GB for a single multi-megapixel scan, and PSNR on phone-scanned pages is ~31 dB at normal settings (visually clean, see below).

## Defects the verification found (fixed)

1. **Normal-mode row pruning removed row-level number formats and fonts.** Excel showed rows 201+ of the bloated sheet change from Courier New / `0.00` to the default. The research item to drop empty rows with an "invisible" style is only right below the data in aggressive mode. Normal mode now keeps any row with a non-default style (`s` != 0), hidden, grouped and resized rows, and only drops rows that restate defaults; aggressive drops row styles and custom heights below the data. After the fix Excel reports zero differences for the normal-mode workbook (formulas, values, formats, merges, hidden/grouped rows and columns, print setup, names). Cost: the test workbook with the 150,000 formatted rows shrinks 19.6% in normal mode instead of 91% (that needs aggressive).
2. **A damaged zip entry was laundered into a valid-looking package.** .NET does not check entry CRCs, so a media entry with a corrupted checksum was copied into a new archive with a fresh, correct CRC. Every entry is now verified while it is read, and a mismatch fails the run with the original untouched.
3. **Replacing the original was not atomic.** `File.Copy(overwrite)` truncates the target first; a crash or full disk mid-copy leaves a broken file where the user's original was. PDF and document outputs now go to a hidden neighbour file and replace the target in one step (`File.Replace`, which keeps ACLs). A locked target now fails cleanly and leaves the original byte-identical.
4. **Memory.** Three image workers made the 8 MB phone-scan PDF peak at 2.7-3.2 GB. A pixel budget (12 MP in flight) now runs big pictures one at a time and small ones in parallel: same output, peak 1.1 GB, 72 s instead of 35 s for that file. Many small pictures still run three at a time.

## What the numbers say

- **PDF vs `main`:** the new code is smaller or equal on every file and where it differs the reason is known: phone-scanned notes (`real02`, `real03`) went from 0% (the old code skipped them) to 35-43% (66-69% aggressive); the iText manual (`real04`) 6.5% -> 65.5%; true `/Indexed`/`/CalRGB` file 0% -> 98.9%; the 96-page lab manual 22.9% -> 25.0% in half the time (100 s vs 201 s). One file is *larger* than `main` on purpose: the `/UserUnit 4` copy (0.83 MiB vs 0.35 MiB), because `main` ignored `/UserUnit` and downsampled pictures that were actually only 150 dpi.
- **Visual:** text, page boxes, links, annotations and form fields (names, types, values) are identical on every PDF. Pixel differences exist only where pictures were re-encoded or downsampled. Looked at side by side: handwriting in the scanned notes (diff only along stroke edges), the Chrome screenshot (indexed 4-bit, max channel difference 26), and the soft-masked cut-out (no halos, max difference 21, soft edge intact). Palette charts were pixel-identical.
- **Scans:** lowest PSNR is 30.9 dB on the phone-scanned notes at normal settings (1.6-1.7% of pixels differ by more than 32 levels, all on pen strokes and paper texture); aggressive is ~28 dB. The synthetic noisy scan is 31.7 dB.
- **Metadata** (Strip metadata is on by default): Info keys except `modDate` and XMP are removed; PieceInfo is removed; links, annotations and the three AcroForm fields survive. Chrome/Word/PowerPoint `creator`/`producer`/`title` are removed too.
- **Office:** all outputs open in Word, PowerPoint, Excel and LibreOffice with no dialog; page counts and text equal; picture-only differences. The deck with 5 duplicate and 6 unused media files went 38.5 -> 6.8 MiB (normal), 0.9 MiB (aggressive); a picture placed through a scaled group was reduced to the size the group displays it at; a picture used as both a shape fill and a slide background kept the resolution the background needs.
- **ODF/EPUB:** see section 4. Office-saved ODF keeps pictures under `media/`, which the optimiser does not look at, so those three files are correctly reported "already optimal" (no gain, nothing rewritten). LibreOffice-saved files (`Pictures/`) shrank 16-64%.

## Known limits and things to decide

1. **Aggressive mode vs blank formatted templates.** In the generated workbook, `Template` (borders on A3:H42, a merged title row, no data) lost its borders: used range A1:H42 -> A1:H1. This is the documented "drop formatted blanks below the data" behaviour, which treats a merged title as the last data row. It is not new, but a printable form is exactly what it hurts. Options: leave as documented, or keep visible formatting within N rows below the data.
2. **Memory.** Single multi-megapixel pictures cost about 1 GB (image pipeline, not new); 12 parallel jobs in one process reached 3 GB. If the app's coordinator can start many jobs at once, a global budget would be needed; this change bounds only each job.
3. **Hard kill leaves work files in `%TEMP%`** (no finalizer can run). The same was true before; this branch did not change that. A startup sweep of `squish-pdf-*` older than a day would fix it.
4. **Pre-damaged inputs are shrunk, not rejected,** when only an XML part is malformed (existing, tested behaviour). Word refuses the truncated DOCX before optimisation (the output was not re-tested in Word).
5. **Word tolerates a missing picture relationship silently** (red X), so "opens without dialog" alone would not catch dangling media there; that case is covered by the package checker and the render comparison, not by Word.
6. Two real documents show `qpdf` warnings (`real06`): an out-of-order name tree that is in the original and unchanged in the output.
7. Office-saved ODF pictures under `media/` are not optimised (see above). Crop trimming, shared-strings/styles cleanup, pivot caches, unused slide layouts, inline PDF images, PDF object merging and SVG are still not implemented (as listed when the branch was delivered).
8. Race on the same output name between two processes can make one of them fail with an IO error; the file left is always a complete result.
